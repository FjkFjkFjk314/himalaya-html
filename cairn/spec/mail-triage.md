# Mail triage

Each configured inbox has a persistent cursor. The first successful poll establishes a baseline. The feeder processes newer messages in order and preserves mailbox flags. An independent watchdog samples host reachability and each inbox’s last successful sync once per minute. It submits a critical Bark alert after a signal has been stale for more than fifteen minutes, suppresses per-mailbox alerts during host outages, sends an ordinary recovery notification, and rearms after recovery.

For messages requiring model classification the classifier tries the primary model first. On provider unavailability it sends the same bounded, locally redacted excerpt to the configured fallback model. If neither provider is available the cursor stays on the pending message for retry. Offline OCR can supply additional text from size-limited raster images. The pipeline excludes remote images and links from retrieval. Classification allows important, routine, promotional, spam, or review. Only important messages enter owner mail memory. By default they trigger immediate encrypted mail notifications. Each summary contains a topic, action, and available date or validated excerpt. The sender encrypts the notification with AES-256-CBC, PKCS7 padding and a fresh random IV before forwarding it to the push service. The classifier rates important mail as normal or urgent using its content and the consequences of delay. Normal mail uses active notifications and urgent mail uses time-sensitive notifications. Existing pending messages without an urgency rating use active notifications. The owner can retrieve records as untrusted data. Delivery state survives restarts and distinguishes confirmed acceptance from an uncertain outcome.

Owner chat is available over local CLI and Lody ACP. It persists session history. An owner can explicitly save a fact for recall from another session or interface. The model may read important-mail records and owner facts. Only owner input can write owner facts. The owner agent uses a private network with HTTPS egress restricted to the configured primary and fallback inference providers. Owner chat uses the fallback during primary-provider outages and automatically returns to the primary when available.

Routine GitHub Actions test-run failures are identified from their notification metadata. They appear as 普通 in the inbox and are collected in a single encrypted daily Bark digest at ordinary priority. Repeated failures are counted. Empty digests are skipped. A designated development audit workflow failure can also use this routine path when the repository, workflow and branch all match. Deployment, production and security incidents remain eligible for individual triage.

The owner assistant uses conversational Chinese by default, leads with the most relevant information and states uncertainty when evidence is incomplete. The owner can explicitly save a preferred tone for subsequent CLI and ACP sessions. In owner chat, the assistant can also persist changes to its SOUL.md tone, level of detail and initiative directly from conversational feedback. It can inspect its current traits and restore a previous combination. Explicit owner preferences take precedence. Personality edits cannot modify mail permissions, notification rules or the unattended classifier.

In either interface the owner can list notification rules and ask in ordinary language to add or remove one. The assistant stages a proposal with its scope and delivery action. Approval requires an explicit, expiring, single-use confirmation through an owner interface. Mail and OCR text are reference data and cannot approve changes.

Rules match all supplied criteria: an exact sender address or domain, a literal subject fragment, a recognized GitHub Actions failure, or its exact repository. For newly classified important mail and recognized routine failures, the newest matching rule selects ordinary, time-sensitive, daily digest or silent delivery. Rules preserve classification, important-mail memory and previously queued delivery decisions. Promotional, spam and review mail stay silent. Host and mailbox health alerts continue to use the independent watchdog.

Owner chat can query open issues assigned to the current Redmine identity through a read-only MCP adapter. A four-minute monitor establishes an initial baseline and persists subsequent changes across restarts. Each issue newly entering a complete snapshot queues an ordinary encrypted Bark notification with its number and subject. Title edits alone do not trigger notifications. An issue observed leaving and later returning can trigger another notification. Failed reads do not replace the baseline.
